# Phase 2–5 실행 계획

이 문서는 계획입니다. 아래 단계는 이번 빌드에서 실행하지 않았습니다. 상태를 성공으로 적지 않습니다.

## Phase 2 — Gazebo / Nav2

목표: `FMS task → 로봇별 에이전트 → Nav2 NavigateToPose → Gazebo Pinky → SUCCEEDED → FMS COMPLETED`.

조건:

- 에이전트 프로세스만 ROS 도메인 73에 참여하고, API 프로세스는 참여하지 않습니다.
- DDS 설정은 `config/cyclonedds.fms.xml` 을 현장 NIC에 맞게 고친 뒤 로드합니다. 기존 Care-Move 도메인과 같으면 시작하지 않습니다.
- 토픽 이름은 그 시뮬레이터의 네임스페이스를 읽은 뒤에 고정합니다. 지금은 이름을 단정하지 않습니다.
- 완료 조건은 지금과 같습니다. 액션 결과의 goal id와 위치 관측이 DB epoch와 맞아야 합니다.
- `/cmd_vel` 은 여전히 FMS 경로가 아닙니다.
- 실물 로봇이 같은 네트워크에 있으면 이 단계를 시작하지 않습니다.

검증은 Gazebo 로그의 Nav2 result와 FMS DB 행을 같이 남깁니다. 없으면 NOT_RUN 입니다.

## Phase 3 — Mock 3대 장애 격리

Phase 1 테스트가 이미 Mock 3대의 독립 완료와 1대 오프라인 격리를 봅니다. Phase 3에서 더할 것은 에이전트 프로세스를 실제로 세 개 띄우고, 한 프로세스를 kill 한 뒤 나머지 두 DB 행이 그대로인지 확인하는 일입니다. 아직 하지 않았습니다.

## Phase 4 — 교통

지금: 단일 구역 잠금, 용량 1, 만료로 해제하지 않음, 대기열 없음.

다음에 할 일:

1. 한 작업이 지나는 구역을 순서대로 예약
2. 복도 진행 방향
3. 맞교차는 한쪽만 진입
4. 예약 대기 그래프의 순환을 만들고 싶다면, 그 전에 순환을 거부하는 테스트
5. Gazebo에서 두 대가 실제로 같은 문을 지나가는 장면

예약 행이 생겼다는 사실만으로 충돌 안전을 통과라고 쓰지 않습니다.

## Phase 5 — 실물

이번 요청의 범위 밖입니다. 시작 조건:

- 사용자가 현장 안전 점검을 승인한 뒤
- 기존 프로젝트가 그 로봇의 제어권을 내려놓았다는 기록이 있는 뒤
- 배터리, 모터, odometry, 비상 정지 경로를 읽기 전용으로 확인한 뒤
- 신규 lease가 기존 gateway와 다른 키인지 확인한 뒤

그 전에는 Nav2 goal을 실물에 보내지 않습니다. 승인 없는 시험 결과는 BLOCKED 입니다.

## 통신

Phase 2 에이전트는 FMS와 WebSocket으로 명령, heartbeat, 결과를 주고, Nav2와는 로컬 액션 클라이언트만 둡니다. 한 로봇의 소켓이 끊기면 그 작업만 복구 격리합니다.
